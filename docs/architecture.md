# Architecture

PREDICT-X is an offline NetFlow-V3 host-forecast demo. The shipped host route is `POST /api/forecast/netflow-v3-host`, and `backend/ml/pcap_ingest.py` adds an optional PCAP path that uses Scapy to parse a capture into NetFlow-style columns that are mapped back into the host pipeline. The adapter is a feature approximation of the NetFlow-V3 training schema and was only exercised on the bundled synthetic PCAPs; it is not validated on a labelled PCAP dataset.

The host pipeline in `backend/ml/host_v3.py` aggregates flows into one row per `(60-second window, source host)`, applies the `min_flows=3` filter and the top-host cap, and then builds the 10-window host feature matrix. The model uses the same feature groups as the dataset: FLOW, PACKET, CONCENTRATION, and CONTEXT. The LSTM learns `initial_access`, `lateral_movement`, and `command_and_control` only. Reconnaissance (`TA0043`) and exfiltration (`TA0010`) are separate rule-based heuristics defined in `backend/ml/heuristic_stages.py` and are not part of the learned model or any benchmark table.

The network risk is defined in `backend/ml/host_forecast.py` as the highest host attack probability in the window: `max over hosts of 1 - P(benign)`. This is not a calibrated probability, and the UI and API explicitly warn that the network timeline is a host-max summary rather than a calibrated alert score. Current detection checks the last three observed windows; future hosts are selected from attack probability on the steps after the last observed window. The response includes current hosts, forecast hosts, MITRE tactic, explanatory attributions, and the flagged-window flow drill-down.

The rule-based stages were tested only on synthetic captures generated by `scripts/generate_sample_pcap.py`. In the labelled samples reported in `README.md`, the heuristic rules fired on hosts without dataset labels: benign 0/0, bot 1/0, infiltration 0/0, brute force 2/0, and replay 3/0. That status is unresolved; the repo does not claim validated real-world performance for those rules.

## Benchmark views

The host benchmark is `backend/ml/models/benchmark_v3_host.json`. It reports macro-F1 together with attack-versus-benign precision, recall, and FPR. At host horizon 3, persistence has higher macro-F1 (`0.713145`) than the LSTM (`0.576085`), while the LSTM has lower FPR (`0.006246` vs `0.098204`). This is a persistence-versus-LSTM trade-off, not an overall LSTM win. In the one-attacker brute-force case, the LSTM scores `0.0` F1 on `initial_access`, while it is better on `lateral_movement` and comparable on `command_and_control`.

## Identity diagnostic and limits

`backend/ml/models/diag_hosts.json` reports FPR 0.0054077578 for never-attack hosts and 0.0580991161 for ever-attack hosts, with a volume-matched ratio of 11.1169251. The no-attack-in-test remainder is 6504 rows and 1 false positive after near-attack bands are removed. This does not settle label-boundary effects versus learned host behavior, and the repo does not present a host-disjoint generalisation result. The procedure is also budgeted: leave-one-attack-out and ablation use two-seed procedures, not full-data comparisons.

The brute-force verification is explicit. In the real sample, the active windows reach `0.962` to `0.985` as the highest host probability in the window, and the attacker host `13.58.98.64` is the highest-probability host in those active windows. The stage is `command_and_control`, not the sample label `initial_access`. After the attacker stops, the future probabilities are `0.063`, `0.019`, and `0.017`, and no host is flagged. The repo does not claim a real labelled PCAP benchmark; it only reports this synthetic verification and the synthetic recon/exfil heuristics.

The budgeted procedure caveats and the host-level identity diagnostic are the important limits: attack labels are proxy labels, the evaluation is on one dataset, and the packaged PCAP tests are synthetic rather than labelled production captures.
